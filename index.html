Fundamentos

git init

Cria um repositório Git novo e vazio no diretório atual.

git init                 # inicializa o repositório
git init nome-do-projeto # cria a pasta e inicializa

Quando usar: ao começar a versionar um projeto que ainda não está sob controle de versão.

As três áreas do Git

Working Directoryseus arquivos em edição
Staging (Index)o que entrará no próximo commit
Repositóriohistórico de commits (.git)

git init apenas cria a pasta .git (o Repositório). Nenhum commit existe ainda.

git clone

Baixa uma cópia completa de um repositório remoto, com todo o histórico.

git clone https://github.com/usuario/projeto.git
git clone git@github.com:usuario/projeto.git pasta-local

Quando usar: para obter um projeto existente e começar a trabalhar nele.

O histórico remoto vem inteiro para a sua máquina

gitGraph
   commit id: "A"
   commit id: "B"
   commit id: "C" tag: "origin/main"

Após o clone, você tem o histórico completo localmente e um remoto configurado como origin.

git status

Mostra o estado atual: o que mudou, o que está em staging e em qual branch você está.

git status
git status -s   # formato curto

Quando usar: a qualquer momento, para entender onde você está antes de agir. É uma operação só de leitura — não altera nada.

Working Directoryarquivos modified / untracked
Stagingarquivos staged
Repositóriocommits confirmados

git status olha para as três áreas e resume as diferenças entre elas.

git add

Move alterações do Working Directory para o Staging, preparando o próximo commit.

git add arquivo.txt   # um arquivo
git add .             # tudo na pasta atual
git add -p            # escolher pedaços interativamente

Quando usar: depois de editar arquivos, para selecionar o que entra no commit.

Working Directory
git add →
Staging

git add não cria commit; apenas marca o que será commitado.

git commit

Grava no histórico tudo que está em staging, criando um novo ponto no tempo.

git commit -m "mensagem clara do que mudou"
git commit -am "mensagem"   # add + commit de arquivos já rastreados

Quando usar: quando um conjunto de mudanças forma uma unidade lógica e coesa.

Staging
git commit →
Repositório

Cada commit vira um novo nó na branch

gitGraph
   commit id: "inicial"
   commit id: "funcao login"
   commit id: "corrige bug"

git log

Lista o histórico de commits — autor, data, mensagem e hash.

git log
git log --oneline            # resumido, 1 linha por commit
git log --oneline --graph    # desenha o grafo no terminal

Quando usar: para revisar o que já foi feito. Operação só de leitura — não altera o histórico.

O que o log percorre é exatamente este grafo

gitGraph
   commit id: "a1b2c3"
   commit id: "d4e5f6"
   commit id: "9f8e7d" tag: "HEAD"

Branches e integração

git branch

Cria, lista ou apaga branches. Uma branch é um ponteiro móvel para um commit.

git branch                 # lista as branches
git branch nova-feature    # cria (sem trocar para ela)
git branch -d nova-feature # apaga uma branch já integrada

Quando usar: para isolar um trabalho (feature, correção) sem afetar a linha principal.

A nova branch parte do commit atual

gitGraph
   commit id: "A"
   commit id: "B"
   branch nova-feature
   commit id: "C"

git checkout / git switch

Troca a branch ativa movendo o HEAD. switch é a forma moderna e mais segura.

git switch nova-feature       # troca de branch
git switch -c outra-feature   # cria e já troca
git checkout nova-feature     # forma clássica (equivalente)

Quando usar: para sair de uma branch e trabalhar em outra. O HEAD passa a apontar para a branch escolhida.

HEAD agora segue a branch "nova-feature"

gitGraph
   commit id: "A"
   commit id: "B"
   branch nova-feature
   checkout nova-feature
   commit id: "C" type: HIGHLIGHT

git merge

Junta o histórico de outra branch na branch atual, geralmente criando um commit de merge.

git switch main
git merge nova-feature   # traz a feature para a main

Quando usar: para integrar um trabalho concluído preservando o histórico real de ambas as branches.

O merge preserva as duas linhas e as une em um commit

gitGraph
   commit id: "A"
   commit id: "B"
   branch nova-feature
   checkout nova-feature
   commit id: "C"
   commit id: "D"
   checkout main
   merge nova-feature

O ponto verde é o commit de merge: ele tem dois pais e marca onde as histórias se encontraram.

Conflitos de merge

Acontecem quando duas branches alteram as mesmas linhas de um arquivo (ou uma apaga o que a outra editou) e o Git não consegue decidir sozinho qual versão manter.

Por que ocorre: durante um merge (ou rebase/cherry-pick), o Git combina as mudanças automaticamente quando elas estão em partes diferentes do arquivo. Quando as edições se sobrepõem, ele para e pede sua decisão.

As duas branches mudaram a mesma linha — o merge não fecha sozinho

gitGraph
   commit id: "A"
   commit id: "B"
   branch nova-feature
   checkout nova-feature
   commit id: "C (edita linha 10)"
   checkout main
   commit id: "D (edita linha 10)"

Ao rodar git merge nova-feature nesse cenário, o Git interrompe o merge e marca o arquivo como conflitado.

Dentro do arquivo, o Git insere marcadores de conflito delimitando as duas versões:

<<<<<<< HEAD    preco = valor * 1.10   # sua versão (branch atual / main)=======    preco = valor * 1.15   # versão que entra (nova-feature)>>>>>>> nova-feature

Azul (entre <<<<<<< e =======): o conteúdo da sua branch atual (o "nosso" / ours).
Verde (entre ======= e >>>>>>>): o conteúdo que está sendo integrado (o "deles" / theirs).

Passos para resolver

  1. Veja o que está em conflitogit status lista os arquivos marcados como Unmerged paths.
  2. Abra cada arquivo conflitadoProcure os marcadores <<<<<<<, ======= e >>>>>>>.
  3. Escolha a versão finalEdite o trecho deixando o código correto: pode ser uma das versões, ou uma combinação das duas. Apague todos os marcadores de conflito.
  4. Marque como resolvidoRode git add arquivo para sinalizar ao Git que aquele conflito foi tratado.
  5. Conclua a operaçãoFaça git commit para finalizar o merge (o Git já sugere uma mensagem). Em rebase, use git rebase --continue.
git merge nova-feature       # merge para e avisa do conflito
git status                   # 1. ver arquivos conflitados
# 2-3. editar os arquivos e remover os marcadores
git add arquivo.py           # 4. marcar como resolvido
git commit                   # 5. concluir o merge

Mudou de ideia no meio? git merge --abort cancela o merge e devolve a branch ao estado anterior ao conflito.

Ferramentas ajudam: git mergetool abre um editor visual de conflitos, e editores como o VS Code mostram botões "Accept Current / Incoming / Both" sobre cada bloco.

git rebase

Reaplica seus commits sobre outra base, reescrevendo o histórico para deixá-lo linear.

git switch nova-feature
git rebase main   # reaplica os commits da feature sobre a main

Quando usar: para manter um histórico limpo e linear antes de integrar. Diferente do merge, não cria commit de junção.

Antes do rebase

gitGraph
   commit id: "A"
   commit id: "B"
   branch nova-feature
   checkout nova-feature
   commit id: "C"
   commit id: "D"
   checkout main
   commit id: "E"

Depois do rebase (C e D reaplicados sobre E)

gitGraph
   commit id: "A"
   commit id: "B"
   commit id: "E"
   branch nova-feature
   checkout nova-feature
   commit id: "C'"
   commit id: "D'"

Nunca faça rebase de commits que já foram enviados e compartilhados no remoto: reescrever esse histórico quebra o repositório dos colegas.

git cherry-pick

Copia um commit específico de outra branch para a branch atual.

git switch main
git cherry-pick a1b2c3   # aplica só aquele commit aqui

Quando usar: quando você quer apenas uma correção pontual de outra branch, sem trazer todo o resto.

O commit "C" é copiado para a main

gitGraph
   commit id: "A"
   commit id: "B"
   branch correcao
   checkout correcao
   commit id: "C"
   commit id: "D"
   checkout main
   cherry-pick id: "C"

O cherry-pick cria um novo commit na main com o mesmo conteúdo de "C" (hash diferente). O "C" original continua na branch de origem.

Desfazer e reverter

git reset

Move o ponteiro da branch (e o HEAD) para outro commit. É uma operação local e potencialmente destrutiva.

git reset --soft HEAD~1   # desfaz o commit, mantém tudo em staging
git reset --mixed HEAD~1  # desfaz commit e staging (padrão)
git reset --hard HEAD~1   # desfaz commit, staging E alterações locais

Quando usar: para desfazer commits locais ainda não compartilhados.

Antes — HEAD em "D"

gitGraph
   commit id: "A"
   commit id: "B"
   commit id: "C"
   commit id: "D" tag: "HEAD"

Depois de reset para "B" — "C" e "D" ficam órfãos

gitGraph
   commit id: "A"
   commit id: "B" tag: "HEAD"

O que cada modo faz com suas mudanças ao recuar o commit:

--softmudanças voltam para o Staging
--mixedmudanças voltam para o Working Directory
--hardmudanças são descartadas

git reset --hard apaga alterações não commitadas de forma difícil de recuperar. Use com cuidado.

git revert

Desfaz o efeito de um commit criando um novo commit que inverte as mudanças.

git revert a1b2c3   # cria um commit que desfaz "a1b2c3"

Quando usar: para desfazer algo que já está compartilhado no remoto, sem reescrever o histórico.

Em vez de apagar, adiciona um commit "reverso"

gitGraph
   commit id: "A"
   commit id: "B"
   commit id: "C"
   commit id: "revert C" type: REVERSE

reset vs revert: o reset remove commits movendo o ponteiro (reescreve histórico); o revert preserva o histórico e adiciona um commit que anula o anterior. Em branches compartilhadas, prefira revert.

git stash

Guarda temporariamente mudanças não commitadas e limpa o Working Directory.

git stash            # guarda as mudanças atuais
git stash list       # vê o que está guardado
git stash pop        # recupera e remove da pilha

Quando usar: quando precisa trocar de contexto (ex.: uma correção urgente) sem commitar um trabalho pela metade.

Antes do stash

Working Directorymudanças em andamento

Depois do stash

Working Directorylimpo
Pilha de stashmudanças guardadas aqui

O histórico de commits não muda: o stash vive numa área separada até você aplicar com pop ou apply.

Trabalhando com remoto

git fetch

Baixa commits e referências do remoto, sem alterar suas branches locais.

git fetch origin   # atualiza as refs remotas (origin/*)

Quando usar: para ver o que mudou no remoto antes de integrar, sem riscos.

Antes — local atrás do remoto

gitGraph
   commit id: "A"
   commit id: "B" tag: "main (local)"

Depois do fetch — origin/main atualizou, main local parada

gitGraph
   commit id: "A"
   commit id: "B" tag: "main (local)"
   branch origin/main
   checkout origin/main
   commit id: "C"

Sua branch main continua em "B". Você vê "C" via origin/main, mas ainda precisa integrá-lo.

git pull

É um fetch seguido de integração (merge ou rebase) na branch atual.

git pull                 # fetch + merge (padrão)
git pull --rebase        # fetch + rebase (histórico linear)

Quando usar: para trazer e já aplicar as novidades do remoto na sua branch.

Antes — origin/main tem "C" que você não tem

gitGraph
   commit id: "A"
   commit id: "B" tag: "main (local)"
   branch origin/main
   checkout origin/main
   commit id: "C"

Depois do pull — "C" integrado à main local

gitGraph
   commit id: "A"
   commit id: "B"
   commit id: "C" tag: "main (local)"

fetch vs pull: o fetch só baixa; o pull baixa e já integra na sua branch atual.

git push

Envia seus commits locais para o remoto, atualizando a branch remota.

git push                       # envia a branch atual
git push -u origin minha-branch # 1ª vez: cria e vincula a branch remota

Quando usar: para compartilhar seu trabalho e atualizar o repositório remoto.

Antes — local à frente do remoto

gitGraph
   commit id: "A"
   commit id: "B" tag: "origin/main"
   commit id: "C" tag: "main (local)"

Depois do push — remoto alcança o local

gitGraph
   commit id: "A"
   commit id: "B"
   commit id: "C" tag: "origin/main = main"

Evite git push --force em branches compartilhadas. Se precisar, prefira --force-with-lease, que protege contra sobrescrever trabalho alheio.

Dicas rápidas

  • Faça commits pequenos e com mensagens claras — facilita entender e desfazer depois.
  • Rode git status sempre antes de add/commit para evitar surpresas.
  • Em branches compartilhadas, prefira merge/revert a rebase/reset.
  • Perdeu um commit após um reset? Procure em git reflog antes de entrar em pânico.
